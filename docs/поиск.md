# Как устроен поиск

Разбор механизма целиком: что считается, почему именно так и где границы.
Практическая часть — README, раздел «Поиск». Здесь теория и обоснования.

Код: `src/db/queries/search.ts` (запросы), `src/domain/search.ts` (сборка),
`src/lib/rrf.ts` (слияние), `src/lib/chunk.ts` (нарезка),
`src/lib/embeddings.ts` (векторизация).

---

## Задача

Найти свою заметку, не помня, какими словами она написана.

```
запрос:  «как я делал дробную сортировку»
заметка: «position numeric(20,10), новое значение — среднее между соседями»
```

Ни одного общего слова. Поиск по подстроке и полнотекстовый поиск здесь
одинаково бесполезны: сопоставлять нужно смысл, а не символы.

Обратный случай столь же реален:

```
запрос:  «OAuthAccountNotLinked»
```

Здесь наоборот — нужно точное совпадение. Смысловой поиск такой запрос
размывает: для модели это «что-то про авторизацию», и она с удовольствием
вернёт пять заметок про OAuth, среди которых нужной может не оказаться.

Два запроса требуют противоположных механизмов. Поэтому работают оба, а
результаты сливаются.

---

## Слой 1. Полнотекстовый

### tsvector: текст как мешок лексем

PostgreSQL не ищет по строке. Он приводит текст к `tsvector` — отсортированному
списку **лексем** (нормализованных основ слов) с позициями:

```sql
select to_tsvector('russian', 'Решение про доступы гостя');
--  'гост':4 'доступ':3 'решен':1
```

Три вещи произошли сразу:

1. **Стемминг.** «Решение» → `решен`, «доступы» → `доступ`, «гостя» → `гост`.
   Словоформы схлопнулись в общую основу, поэтому «доступ», «доступы»,
   «доступам» — одно и то же слово для поиска.
2. **Стоп-слова выброшены.** Предлога «про» в результате нет: он есть почти
   в каждом тексте и потому не различает документы.
3. **Позиции сохранены** (`:1`, `:3`, `:4`) — по ним потом считается ранг и
   работает поиск фраз.

Конфигурация `'russian'` — не косметика. С `'english'` русский текст не
стеммится вообще, и «доступы» перестанет находиться по запросу «доступ».

### Где он лежит

В `notes.search_vector` — **генерируемой** колонке (`src/db/schema.ts`):

```sql
to_tsvector('russian', coalesce(title, '') || ' ' || coalesce(content, ''))
```

Генерируемая — значит Postgres пересчитывает её сам при каждой записи.
Рассинхронизировать её с текстом невозможно в принципе: нет кода, который
мог бы забыть обновить. Это работает потому, что `to_tsvector` с **явно
указанной** конфигурацией immutable; без явной `'russian'` функция зависела бы
от настройки сессии, перестала быть immutable и в генерируемую колонку
её бы не пустили.

Поверх — GIN-индекс `notes_search_idx`. GIN (Generalized Inverted Index) —
обратный индекс: для каждой лексемы хранится список документов, где она
встречается. Ровно та структура, которой пользуются поисковые движки:
поиск по слову — это чтение готового списка, а не просмотр таблицы.

### tsquery: разбор запроса

Запрос тоже становится деревом лексем. Три функции разбора, и выбор между
ними — не вкусовщина:

| Функция | Вход | Поведение на мусоре |
| :-- | :-- | :-- |
| `to_tsquery` | строгий синтаксис `слово & слово` | **исключение** |
| `plainto_tsquery` | просто слова, все через AND | молча игнорирует операторы |
| `websearch_to_tsquery` | синтаксис поисковика | не падает никогда |

Выбран `websearch_to_tsquery`, потому что на вход приходит то, что человек
набрал в поле, а не то, что он должен был набрать:

```sql
select websearch_to_tsquery('russian', '"точная фраза" -исключение OR другое');
--  'точн' <-> 'фраз' & !'исключен' | 'друг'
```

Кавычки стали поиском фразы (`<->` — «следует непосредственно за»), минус —
отрицанием, `OR` — дизъюнкцией. С `to_tsquery` тот же ввод дал бы
`syntax error in tsquery`, то есть 500 на пустом месте.

### ts_rank: насколько хорошо совпало

`ts_rank(search_vector, query)` возвращает число тем больше, чем чаще и
«весомее» встретились слова запроса. Абсолютное значение смысла не имеет —
это не вероятность и не проценты, шкала не нормирована. Сравнивать можно
только ранги внутри одной выдачи. Запомним это: через два раздела на этом
факте будет построено всё слияние.

### Чего он принципиально не может

- **Синонимы и переформулировки.** «Права доступа» и «кто что видит» для
  него — разные множества лексем, пересечение пусто.
- **Смысл.** Он сравнивает нормализованные строки, ничего не зная о том,
  что `numeric(20,10)` имеет отношение к сортировке.

## Слой 2. Векторный

### Что такое эмбеддинг

Модель отображает текст в точку многомерного пространства так, что близкие
по смыслу тексты оказываются рядом. Для `bge-m3` это 1024 числа:

```
«права доступа»      → [0.021, -0.113, 0.077, …]   1024 значения
«кто что видит»      → [0.019, -0.108, 0.081, …]   ← рядом
«рецепт борща»       → [-0.204, 0.311, -0.019, …]  ← далеко
```

Никакого понимания языка в момент поиска не происходит: понимание было
«запечено» в веса при обучении, а во время работы модель просто считает
функцию. Поэтому индексация — разовая работа, а поиск — арифметика.

### Косинусное расстояние

Близость меряется углом между векторами, а не расстоянием между точками:

```
cos(a, b) = (a · b) / (|a| · |b|)
расстояние = 1 − cos(a, b)
```

0 — направления совпадают, 1 — перпендикулярны, 2 — противоположны.

Угол, а не евклидово расстояние, потому что длина вектора у эмбеддингов
несёт мало смысла и заметно зависит от длины текста. Два текста об одном и
том же, но на абзац и на страницу, дадут векторы разной длины и почти
одинакового направления. Евклидова метрика посчитала бы их далёкими.

В pgvector это оператор `<=>`.

Побочное следствие, о которое легко споткнуться: **нулевой вектор
недопустим**. У него нет направления, `|b| = 0`, деление на ноль даёт `NaN`,
и сортировка молча ломается. В тестах поэтому у подставного векторизатора
последняя координата всегда `0.01` — см. `tests/search.test.ts`.

### Модель

`bge-m3` из MWS GPT Model Hub:

| | |
| :-- | :-- |
| Размерность | 1024 |
| Окно | 8192 токена |
| Языки | 100+, русский в их числе |
| Симметричность | одна модель и для заметок, и для запросов |

Размерность зашита в тип колонки `vector(1024)` через `EMBEDDING_DIMENSIONS`
в схеме. Держать её в переменной окружения было бы хуже: рассогласование
конфига и базы вылезало бы ошибкой при каждой вставке, а не при старте.

Клиент проверяет длину пришедшего вектора сам (`src/lib/embeddings.ts`).
Без этой проверки ошибку выдал бы Postgres — но уже в терминах типа
`vector`, и настоящая причина («в конфиге не та модель») потерялась бы.

### Чего не может он

- **Точные редкие термины.** `OAuthAccountNotLinked` модель раскладывает на
  подслова и усредняет — получается «что-то про авторизацию».
- **Однословные запросы.** Одному слову не хватает контекста, вектор выходит
  размытым.
- **Сказать «ничего не нашлось».** Об этом отдельно ниже.

## Отсечка по расстоянию

Векторный поиск — это «верни N ближайших соседей». Ближайшие есть **всегда**,
даже если все они бесконечно далеки. Понятия «не подошло» у него нет.

Практическое следствие обнаружилось сразу на живых данных: запрос «рецепт
борща со сметаной» в базе про разработку вернул все заметки подряд.

Замер на шести запросах против реальных заметок:

| Запрос | Ближайшее расстояние |
| :-- | --: |
| доступы | 0,3801 |
| кто имеет право видеть записи | 0,4698 |
| права гостя и владельца | 0,5541 |
| прогноз погоды на выходные | 0,6715 |
| рецепт борща со сметаной | 0,6984 |
| как починить карбюратор мотоцикла | 0,7454 |

Разрыв между худшим осмысленным (0,5541) и лучшим посторонним (0,6715)
чистый. `MAX_SEMANTIC_DISTANCE = 0.65` поставлен в этот зазор, ближе к
верхней границе: пропустить лишнюю заметку дешевле, чем потерять нужную,
а точные словесные совпадения порог не трогает вовсе — их приносит FTS
по своему каналу.

**Число привязано к модели.** У другой модели шкала другая, и 0,65 может
отсечь либо всё, либо ничего. При смене провайдера — перемерить.

## Слияние: RRF

### Почему нельзя просто сложить

Два слоя вернули по списку. Надо получить один. Первая мысль — сложить
оценки — не работает:

```
ts_rank:               0.1873    шкала неизвестна, ненормирована
косинусное расстояние: 0.4698    0…2, и МЕНЬШЕ значит ЛУЧШЕ
```

Числа не только в разных диапазонах, но и направлены в разные стороны.
Привести их к общей шкале можно лишь подбором коэффициентов под конкретные
данные — а подобранные на трёх заметках коэффициенты развалятся на трёхстах.

### Идея

Выбросить оценки. Оставить только **места** в списках.

Место — устойчивая величина: «третий по релевантности» значит одно и то же
независимо от того, чем считали. Это и есть Reciprocal Rank Fusion
(Cormack et al., 2009):

```
score(d) = Σ  1 / (k + rank_i(d))
           i
```

где `rank_i(d)` — место документа `d` в списке `i` (с единицы), а суммирование
идёт по спискам, где документ вообще встретился. `k = 60` — константа,
подобранная авторами эмпирически и с тех пор ставшая значением по умолчанию.

### Зачем нужна k

Она сглаживает разрыв между верхними местами. Без неё (`k = 0`) первое место
даёт 1, второе 0.5 — вдвое меньше. Лидер любого списка становился бы
непобедимым, и слияние вырождалось бы в «кто первый в самом длинном списке».

При `k = 60` вклады соседних мест почти равны:

| Место | `1/(60+i)` |
| --: | --: |
| 1 | 0,016393 |
| 2 | 0,016129 |
| 3 | 0,015873 |
| 10 | 0,014286 |

Разница между первым и вторым — полтора процента. Поэтому **две умеренные
находки перевешивают одну отличную**: документ, найденный обоими слоями на
вторых местах, получает 0,032258 и обгоняет чужого лидера с его 0,016393.

Ровно это и требуется. Заметка, которую независимо нашли и слова, и смысл,
почти наверняка та самая.

### Разбор на числах

Полнотекстовый нашёл `[A, B]`, векторный — `[C, B]`:

| | FTS | вектор | Итого |
| :-- | --: | --: | --: |
| A | 1/61 = 0,016393 | — | 0,016393 |
| B | 1/62 = 0,016129 | 1/62 = 0,016129 | **0,032258** |
| C | — | 1/61 = 0,016393 | 0,016393 |

`B` первая, хотя не была первой нигде.

### Неочевидное свойство

Функция `1/(k+x)` выпуклая, поэтому разнесённые места дают больше, чем два
одинаковых средних:

```
1/61 + 1/63 = 0,0322664      места 1 и 3
2/62        = 0,0322581      места 2 и 2
```

Разрыв ничтожный (восемь миллионных), но знак именно такой. Документ,
который в одном списке лидер, а в другом третий, обгоняет документа,
дважды вторым. Это следствие неравенства Йенсена, а не ошибка.

На это легко попасться, придумывая тесты: интуиция подсказывает обратное.
Проверка на симметричных списках `[A,B,C]` и `[C,B,A]` даст победителями
`A` и `C`, а не `B`.

### Что даётся бесплатно

- Пустой список не мешает: если внешний API отказал, `fuseByRrf([[…], []])`
  вырождается в исходный полнотекстовый порядок. Отдельной ветки «если
  вектора нет» в коде нет.
- Списки могут быть разной длины и не пересекаться.
- Нет ни одного параметра, который надо подбирать под данные.

Порядок при равных очках фиксируется по `id` — иначе один и тот же запрос
давал бы разную выдачу от вызова к вызову.

## Нарезка

Модель не принимает текст любой длины. Окно `bge-m3` — 8192 токена, лимит
заметки — 512 КБ. Заметка может превысить окно в десятки раз.

Что случилось бы без нарезки: текст сверх окна либо вызвал бы ошибку, либо
молча обрезался. Второе хуже. Поиск выглядел бы полностью рабочим, но был бы
систематически слеп ко всему после первых килобайт — и заметить это можно
только случайно.

Алгоритм (`src/lib/chunk.ts`), от крупного к мелкому:

1. По заголовкам markdown — они и есть авторская разбивка на темы.
2. Если раздел всё равно велик — по абзацам, набирая их в кусок жадно.
3. Если абзац сам больше бюджета — по границе слова.

**Бюджет 12 000 символов**, не 8192 токена. Токенизатор `bge-m3` в Node ради
редкой проверки тащить не стали: для русского выходит 2–3 символа на токен,
то есть 12 000 символов — это 4–6 тысяч токенов, ниже потолка даже при
худшем соотношении. Запас намеренно перекошен: разрезать лишний раз
безвредно, не разрезать когда надо — нет.

Две детали, каждая из которых иначе давала бы тихую порчу:

- **Состояние ограждённого блока.** `# comment` внутри ` ``` `-блока — это
  bash, а не заголовок. Без отслеживания фенсов нарезка рвала бы код
  посередине.
- **Пустая заметка обязана дать один кусок**, а не ноль. Ноль строк в
  `note_chunks` означает «не проиндексирована», и такая заметка попадала бы
  в переиндексацию при каждом поиске, бесконечно тратя вызовы API.

Заголовок заметки приписывается к каждому куску перед отправкой в модель
(`embeddingInput`), но **не** сохраняется в текст куска. Причина в двух
разных потребителях: модели нужен контекст (второй кусок сам по себе
теряет тему), а пользователю в сниппете заголовок не нужен — он и так
написан строкой выше.

## Индексация и устаревание

### Почему не при сохранении

Редактор автосохраняется постоянно. Пересчёт векторов на каждый `PATCH`
означал бы вызов внешнего API на каждые несколько нажатий клавиш.

Индексация ленивая: правка ничего не пересчитывает, а отставание
устраняется при ближайшем поиске. Задержку там и так прячет пауза перед
смысловым запросом.

### Хеш вместо флага

Устаревание определяется сравнением, а не отметкой:

```sql
not exists (
  select 1 from note_chunks c
  where c.note_id = n.id
    and c.source_hash = md5(n.title || n.content)
)
```

Флаг «надо переиндексировать» можно рассинхронизировать с данными: упавшая
запись, правка мимо приложения, восстановление из бэкапа. Хеш вычисляется
из самих данных, поэтому рассинхронизация невозможна по построению — схема
самовосстанавливающаяся.

Хеш считает база и она же его возвращает; приложение записывает обратно
ровно то, что получило. Побочно это решает гонку: если текст изменился,
пока считались векторы, записанный хеш не совпадёт с новым содержимым, и
следующий поиск пересчитает. Тот же приём, что у кеша рендера в
`saveNoteHtml`.

`title || content`, а не только `content`: заголовок уходит в модель вместе
с текстом, значит его правка меняет вектор.

## Поведение при вводе

Два запроса вместо одного, потому что у слоёв разная цена:

```
нажатие клавиши ──120 мс──> mode=fts     локально, бесплатно  → список сразу
пауза в наборе  ──400 мс──> mode=hybrid  вызов API, деньги    → список уточняется
```

Полнотекстовый успевает ответить раньше, чем человек заметит задержку, и
поиск ощущается мгновенным. Смысловой уходит, только если человек
действительно остановился — иначе каждое нажатие клавиши стоило бы вызова
модели.

Две тонкости на клиенте (`src/components/search/search-palette.tsx`):

- **Гибридный ответ не затирается полнотекстовым.** Сеть не обещает порядок:
  запущенный раньше FTS может вернуться позже. Откат к худшей выдаче
  заметен глазом, поэтому есть флаг, кто уже ответил.
- **`AbortController` на смену строки.** Иначе ответы на устаревшие запросы
  наперегонки перезаписывали бы список.

`Ctrl+K` перехватывается с `preventDefault`: в Chrome и Firefox это
сочетание уводит фокус в адресную строку.

## Деградация

Векторы считает внешний сервис. Он может быть недоступен, ключ может
протухнуть, лимит может кончиться.

Правильный ответ в этой ситуации — **не 500, а поиск по словам**:

```
ошибка векторизации → catch → выдача полнотекстового слоя, semantic: false
```

Полнотекстовый список вычисляется **первым и всегда**, до всякого обращения
к сети, — именно чтобы ему было чем стать ответом. Пустой `MWS_API_KEY` —
тот же путь, только без исключения: штатный режим, а не поломка.

Это и есть главный практический аргумент за гибрид. Качество — второй.

## Границы механизма

Что он **не** делает и не будет:

- **Не генерирует ответы.** Заметки написаны вами; нужно вспомнить и попасть
  в свой текст, а не прочитать его пересказ. Ошибка ранжирования видна и
  исправляется глазами за секунду, ошибка пересказа — нет, потому что
  источнику вы доверяете.
- **Не ищет по чужим заметкам.** Общего каталога в сервисе нет.
- **Не ищет по архивным.**

Фильтр по владельцу стоит **внутри** ранжирующего запроса, до `limit`.
Отфильтровать чужое после выборки top-N нельзя: top-N мог бы целиком
состоять из чужих заметок, и владелец получил бы пустоту при живых
совпадениях в своих.

## Замеренное

Локально, база из трёх заметок, `bge-m3`:

| Операция | Время |
| :-- | --: |
| `mode=fts` | 18–68 мс |
| `mode=hybrid` (индекс актуален) | 61–90 мс |
| `mode=hybrid` (с индексацией трёх заметок) | ~200 мс |

Стоимость: 0,61 ₽ за миллион входящих токенов. Полная переиндексация базы
из полусотни заметок — около пяти копеек.

Проверка «понимает ли модель русский» — `tests/embeddings-live.test.ts`,
единственный тест, ходящий в сеть; без ключа пропускается.

## Что отложено и почему

Подробно — `docs/следующие-шаги.md`, раздел «Поиск: что отложено сознательно».
Коротко:

- **Реранкер** (cross-encoder, у MWS есть и сейчас бесплатен) — на десятках
  заметок переупорядочивал бы почти всю базу, выигрыш около нуля.
- **HNSW-индекс** — до тысяч векторов полный перебор быстрее обхода индекса,
  а индекс ещё и приблизительный, то есть меняет выдачу.
- **Сравнение с Yandex AI Studio** — когда накопятся живые запросы, на
  которых видно, что выдача неидеальна.
