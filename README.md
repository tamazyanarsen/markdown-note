# md-note

Личное дерево заметок в markdown с постоянными ссылками на папки и заметки.

Доменная модель, схема БД и правила доступа описаны в
[`docs/описание.md`](docs/описание.md) — это источник истины.
Расхождения реализации с документом перечислены в конце этого файла.

Что сделано, что проверено и что осталось —
[`docs/следующие-шаги.md`](docs/следующие-шаги.md).

## Как это работает

Два вида ресурсов, у каждого — UUID, который одновременно первичный ключ
и идентификатор в ссылке:

```
/f/:folderId    папка
/n/:noteId      заметка
```

Заметка бывает `private` или `public`. У папки собственной видимости нет.
Вложения своей видимости тоже не имеют — она берётся у заметки, к которой
файл прикреплён.

| Кто открывает | `/n/:id` private | `/n/:id` public | `/f/:id` |
| :-- | :-- | :-- | :-- |
| Владелец | заметка | заметка | всё поддерево |
| Гость | `404` | заметка | только public-заметки и папки на пути к ним |
| Другой пользователь | `404` | заметка | то же, что гость |

Private-заметка не попадает в публичный ответ вообще: ни UUID, ни заголовок,
ни время изменения.

## Стек

Next.js 16 (App Router, TypeScript) · PostgreSQL 17 + pgvector · Drizzle ORM ·
Auth.js v5 (GitHub / Яндекс / VK ID) · CodeMirror 6 · remark/rehype ·
dnd-kit · Tailwind CSS 4 · Docker Compose за nginx

## Локальный запуск

```bash
cp .env.example .env          # заполнить AUTH_SECRET: npx auth secret
npm install
npm run db:up                 # Postgres в Docker
npm run db:migrate            # схема, индексы, триггеры
npm run dev
```

Без OAuth-приложений страница входа скажет, что провайдеров нет. Заведи хотя бы
GitHub: https://github.com/settings/developers, callback
`http://localhost:3000/api/auth/callback/github`.

> **Если том базы создан до появления поиска.** Образ сменился с
> `postgres:17-alpine` на `pgvector/pgvector:pg17`, а это musl → glibc.
> Правила сортировки текста у них разные, и индексы по `text` от них зависят.
> После первого старта на новом образе выполнить один раз:
>
> ```bash
> docker compose exec postgres psql -U mdnote -d mdnote -c "REINDEX DATABASE mdnote;"
> ```
>
> Для чистого тома этого не нужно: он сразу создаётся новым образом.

│  ├─ chunk.ts  rrf.ts         нарезка заметок и слияние выдач
│  ├─ embeddings.ts  chat.ts   векторизация и генерация во внешнем API
│  ├─ uploads.ts               файлы вложений на диске
│  ├─ errors.ts                доменные ошибки → HTTP-коды
│  └─ rate-limit.ts
└─ components/
```

Тесты лежат в трёх местах, и деление не случайное: `src/**/*.test.ts` —
чистые функции рядом с кодом, `tests/` — доменный слой против настоящего
Postgres, `e2e/` — браузер поверх поднятого приложения. Последние проверяют
то, до чего первые два не достают: перехват `Ctrl+K`, автодополнение по `[[`,
вставку картинки из буфера и режим ответа в палитре.

Правило слоёв: route handler занимается только HTTP, все проверки прав — в
`src/domain`. Ни один запрос на изменение не ищет ресурс по одному лишь `id`,
всегда по паре `(id, owner_id)`.

## Поиск

`Ctrl`/`Cmd` + `K` — палитра поиска по своим заметкам. Ищет по смыслу, а не
только по совпадению слов: запрос «дробная сортировка» находит заметку, где
написано `position numeric(20,10)` и нет ни одного слова из запроса.

Работают два слоя, и их результаты сливаются по местам —
[RRF](src/lib/rrf.ts), `score = Σ 1/(60 + позиция)`:

| Слой | Чем считается | Когда уходит запрос |
| :-- | :-- | :-- |
| Полнотекстовый | `websearch_to_tsquery('russian')` по `notes.search_vector` | на каждое нажатие клавиши |
| Смысловой | косинусное расстояние pgvector по `note_chunks` | после паузы в наборе |

Слияние, а не замена — потому что слои промахиваются по-разному. Векторный
размывает точные термины (`OAuthAccountNotLinked` превращается в «что-то про
авторизацию»), полнотекстовый слеп к переформулировкам. По рангам, а не по
самим оценкам: `ts_rank` и косинусное расстояние живут в разных шкалах.

У векторного слоя есть отсечка по расстоянию (`MAX_SEMANTIC_DISTANCE` в
`src/db/queries/search.ts`). Без неё запрос не по теме возвращал бы всю базу:
ближайшие соседи находятся всегда, понятия «ничего не подошло» у векторного
поиска нет. Порог измерен на живых данных — у релевантных запросов ближайшее
расстояние 0,38–0,55, у посторонних 0,67–0,75.

**Без ключа поиск не ломается, а остаётся полнотекстовым.** Пустой
`MWS_API_KEY` — штатный режим; то же самое происходит, если внешний API
недоступен или ответил ошибкой. Обратное — 500 вместо рабочего поиска по
словам — было бы худшим из вариантов.

Векторы считает [MWS GPT Model Hub](https://mws.ru/cloud-platform/model-hub/),
модель `bge-m3` (1024 измерения, окно 8192 токена, OpenAI-совместимый API).
API совместимый, поэтому смена провайдера — это `MWS_BASE_URL`,
`MWS_EMBEDDING_MODEL`, размерность в `EMBEDDING_DIMENSIONS` и переиндексация.

Индексация ленивая: заметка не пересчитывается при сохранении (редактор
автосохраняется постоянно, каждая правка стоила бы вызова API), а отстаёт до
ближайшего поиска. Устаревание определяется сравнением `note_chunks.source_hash`
с `md5(title || content)`, а не флагом — хеш нельзя рассинхронизировать
с данными.

HNSW-индекса по векторам нет намеренно: на текущих объёмах полный перебор
быстрее обхода индекса.

Как всё это устроено внутри — `tsvector` и стемминг, косинусное расстояние,
математика RRF, нарезка и устаревание векторов — [`docs/поиск.md`](docs/поиск.md).

## Вопрос к заметкам

Первым пунктом в палитре — «Спросить у заметок». Тот же гибридный поиск, но
верхние пять заметок уходят в языковую модель, и вместо списка приходит ответ
со ссылками на источники: `[1]`, `[2]` в тексте совпадают с номерами в списке
под ним.

Модель получает только куски найденных заметок и прямой запрет отвечать из
собственных знаний. Без него на вопрос, ответа на который в заметках нет, она
уверенно рассказала бы что-нибудь общеизвестное — и отличить это от настоящей
выдержки из своих записей стало бы невозможно.

**Ответ необязателен, источники обязательны.** Если `MWS_CHAT_MODEL` не задан
или провайдер отказал, приходит та же выдача без пересказа — найденные заметки
полезны и без него. Тот же принцип, что у поиска без ключа: деградировать,
а не падать.

Имени модели по умолчанию нет: у эмбеддингов оно есть, потому что размерность
зашита в схему, а здесь выбор широкий и меняется вместе с каталогом Model Hub.

> **Имя в `MWS_CHAT_MODEL` — это имя деплоя, а не строка из каталога.**
> В каталоге модель записана как `qwen3.6-35b-a3b`, а API ждёт
> `qwen3-6-35b-a3b`. Ошибиться легко, и ответ на ошибку — `404
> DEPLOYMENT_NOT_FOUND`, который приложение проглотит: поиск продолжит
> работать, ответы молча перестанут. Проверить, что видит проект:
>
> ```bash
> curl -s -H "Authorization: Bearer $MWS_API_KEY" "$MWS_BASE_URL/models" | jq -r '.data[].id'
> ```

## Связи между заметками

Дерево — это иерархия, а заметки по смыслу связаны сетью. Под редактором две
строки: **«Ссылаются сюда»** и **«Похожие»**. Списки разные намеренно —
обратную ссылку поставил человек, похожесть посчитал косинус, и смешивать
факт с догадкой не стоит.

`[[` в редакторе открывает поиск по своим заметкам, а в текст кладёт обычную
markdown-ссылку на permalink:

```
набрано:  [[дробн
в файле:  [Дробная сортировка](/n/7f3a…)
```

Своего синтаксиса в файле не остаётся. Значит рендер, санитизация, публичная
страница и будущий экспорт про связи не знают ничего, а ссылка живёт в любом
редакторе markdown. Плата одна: переименование заметки не меняет текст ссылок
на неё — сам адрес при этом не ломается, он и задуман неизменным.

Обратные ссылки вычитываются из текста при сохранении, разбором AST, а не
регуляркой: `/n/…` внутри ```-блока — это пример в документации, а не связь.
Цели подбираются по паре `(id, owner_id)`, поэтому связь с чужой заметкой
не появится, даже если ссылка на неё в тексте есть.

«Похожие» считаются по тем же векторам, что уже лежат в `note_chunks` — новых
вызовов внешнего API не появляется. Отсечка у них своя,
`MAX_RELATED_DISTANCE` в [`src/db/queries/search.ts`](src/db/queries/search.ts):
там сравнивается короткий запрос с длинным куском, здесь — длинный текст
с длинным, и шкалы у этих пар разные.

Измерено на bge-m3, восемь заметок и все 28 пар между ними:

| Пары | Расстояние |
| :-- | :-- |
| По одной теме | 0,32 · 0,45 · 0,45 · 0,51 · 0,53 |
| Разные темы | 0,49 … 0,71 |
| Заведомо постороннее | от 0,57 |

Чистого зазора нет, в отличие от пары «запрос — кусок»: диапазоны налезают
друг на друга в районе 0,49–0,53. Это свойство задачи, а не дефект замера —
две заметки одного проекта похожи всегда, вопрос только насколько. Порог 0,55
стоит там, где кончаются настоящие пары и начинается постороннее, с перекосом
в сторону «лучше показать лишнее»: блок дополняет заметку, и одна неточная
подсказка дешевле пустой строки.

## Вложения

Картинка вставляется в редактор из буфера или перетаскиванием: пока файл
летит на сервер, в тексте стоит плейсхолдер, потом на его месте появляется
`![имя](/api/files/…)`.

Права у файла не свои, а заметки-владельца. Публикация заметки открывает её
картинки гостю, возврат в private — закрывает; архивная не отдаёт ничего.
Одна модель доступа вместо двух, которые пришлось бы держать согласованными.

Что можно грузить: png, jpeg, gif, webp и pdf, до 10 МБ. SVG исключён
намеренно — это документ со скриптами внутри, и отдавать его со своего домена
значило бы открыть XSS в обход всей санитизации markdown.

Байты лежат на диске (`UPLOADS_DIR`, в Docker — том `uploads-data`), в базе
только метаданные. Путь не хранится, а выводится из `owner_id` и id вложения:
обе части — UUID из базы, расширение — из белого списка, поэтому имя файла
из формы в путь не попадает вообще.

> **Бэкап теперь из двух частей.** `scripts/backup.sh` делает и дамп базы, и
> архив вложений. Дамп без вложений восстановит заметки со сломанными
> картинками — в базе лежат только ссылки на файлы.

## Доступ

Вход через OAuth открыт всем, но приложение доступно только одобренным.
`ALLOWED_EMAILS` — список email через запятую, которым доступ выдаётся
автоматически при первом входе. Остальные попадают на `/pending`; одобрить
их можно вручную:

```sql
update users set is_approved = true where id = '…';
```

Если `ALLOWED_EMAILS` пуст, регистрация открыта — это режим локальной
разработки, для публичного сервера переменную нужно заполнить.

### Почему нет входа по паролю

Сознательное решение. Credentials-провайдер Auth.js несовместим с
database-сессиями: он всегда кладёт в cookie JWT и не создаёт строку в
`sessions`. Добавить пароль — значит перевести всё приложение на JWT и
потерять отзыв сессий (`delete from sessions`) и актуальность `is_approved`,
который сейчас читается из базы, а не протухает в токене на 30 дней.

Если понадобится вход для человека без Яндекса, VK и GitHub — это magic link,
а не пароль: он работает с database-сессиями, а таблица `verification_tokens`
под него уже есть в схеме. Из нового нужен только SMTP или Resend.

## Деплой

Пошаговая инструкция для чистого сервера — [`docs/деплой.md`](docs/деплой.md).
Коротко:

```bash
cp .env.production.example .env.production   # заполнить пароли, AUTH_URL, OAuth
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
```

Compose поднимает Postgres, одноразовый контейнер миграций (приложение
стартует только после его успешного выхода) и само приложение.

Наружу не смотрит ничего: Postgres доступен только внутри сети compose,
приложение — на `127.0.0.1:3000`. TLS и 80/443 держит системный nginx:
настройки прокси — [`deploy/md-note-proxy.conf`](deploy/md-note-proxy.conf),
готовый `server`-блок для своего домена —
[`deploy/md-note.nginx.conf`](deploy/md-note.nginx.conf). Если домен на
сервере уже настроен и сертификат выпущен, нужен только первый файл.

Бэкапы — `scripts/backup.sh`, в cron на хосте:

```
0 4 * * * /opt/md-note/scripts/backup.sh >> /var/log/md-note-backup.log 2>&1
```

## Отличия от docs/описание.md

Документ писался под редактор Tiptap и обязательный email. Реализация
расходится с ним в пяти местах:

1. `notes.content` — `text` с markdown-исходником, а не `jsonb`.
2. Вместо `notes.plain_text` — генерируемая колонка `search_vector` (`tsvector`)
   с GIN-индексом.
3. `users.email` — nullable: VK не отдаёт email, у GitHub он может быть скрыт.
   Уникальность даёт пара провайдер + внешний id.
4. Добавлены таблицы Auth.js: `accounts`, `sessions`, `verification_tokens`.
5. Добавлены таблицы под то, чего в документе не было: `note_chunks`
   (векторы для поиска), `note_links` (связи между заметками) и `attachments`
   (метаданные вложений).

Остальное — инварианты владения, триггеры, правила перемещения, коды ошибок
и публичная проекция дерева — соответствует документу. Вложения в него
встроены тем же правилом: `attachments_owner_matches_note_owner` — такой же
триггер, как у заметок и папок, а доступ к файлу целиком наследуется
от заметки.
